# Chat image attachments

The chat uses provider-independent attachment references. The first supported kind is `image`; adding text/document formats later requires explicit validation and provider support.

## User flow

With an image-capable provider selected, use the paperclip or paste an image into the composer. Review the thumbnails, remove unwanted images, add an optional message and send. A message may contain images without text. Click a sent thumbnail to open a larger preview.

Initial limits: three images per message, 4 MB per image and 16 million pixels per image. JPEG, PNG and WebP are accepted. The server verifies and decodes the actual content rather than trusting the filename or browser MIME type. Gemini requests are capped at 12 MB of image bytes across the included conversation; reduce images/start a fresh conversation when that limit is reached.

## Persistence

Files are stored in `data/programs/<provider-id>/files/<GUID>`. The filename is generated by the server, without an extension; MIME type is detected from the content. Chat JSON contains an `attachment` part with version, kind, GUID, original display name, MIME type, byte size, width and height. Ordinary messages keep their existing text parts.

Images are not widget assets. They are not stored in local storage, public widget directories or Markdown data URLs. The UI retrieves previews through the selected provider's API. Provider wrappers fix the owner ID; client-supplied paths/owner IDs are not used.

History export includes image bytes in attachment parts so the exported JSON is portable. Import validates files, assigns new GUIDs and removes embedded bytes before saving canonical history. Existing text-only exports remain valid. Failed imports remove newly created files and preserve the existing history.

Clearing the entire history deletes the provider's image files and removes the empty `files` directory. Deleting a single message does not immediately delete its images, since a retry or another browser could still reference them. Abandoned files older than one day are pruned during later uploads/imports. No other provider's files are removed.

## API contract

Each provider exposes:

- `Attachments.Describe`: version, supported kinds/MIME types and upload limits. An empty kind list means the current model is text-only. Older providers without this endpoint remain text-only in YoT.
- `Attachments.Upload`: `{name, data}` with base64 bytes; returns `{Status:"Ok", attachment:{...}}`.
- `Attachments.Get`: `{id}`; returns the detected MIME type and base64 bytes for an authenticated preview.
- `Attachments.Delete`: `{id}`; deletes an unused draft, refusing files still referenced by history.

Structured `Prompt.Submit` accepts `attachments:[{id,name}]` alongside `message`, context and action capabilities. Attachment support is independent of context sharing and device/program/widget capabilities.

Chat History service 577 owns persistence through provider-scoped `Files.*` calls. `Files.Validate` returns canonical metadata; `Files.Resolve` resolves references into a temporary provider-independent copy containing image data. Only the Gemini adapter maps these parts to `inlineData`. Stored history never receives provider payloads.

## Provider status and acceptance

Gemini Genie supports image input. Its context/tool/action follow-ups retain the original image parts; responses keep the existing structured action handling.

The current Lailama catalog/session implementation remains text-only and explicitly rejects image attachments. Native MTMD/projector loading and a verified vision model are a separate integration step; the shared storage/transport does not imply local vision support. Do not advertise image capability based solely on a model-family name.

Automated checks cover storage confinement, file validation, cross-provider isolation, portable export/import, rollback, clearing, text compatibility, provider mapping, retry state, capability changes and image-only messages. Maintainer-confirmed live acceptance (2026-11-02): Gemini described an uploaded image and answered a follow-up about the same image without another upload. Retrieval through the attachment API was also verified. Second-browser history, portable export/import and complete-history cleanup still need live acceptance. No live provider was restarted or charged by the automated tests.
