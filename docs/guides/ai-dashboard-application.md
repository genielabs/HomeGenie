# Apply a dashboard from an AI objective

The objective runner can save widget sources and then apply a saved `defaultSize: 'dashboard'` container to the initiating client preset. Saving an ordinary widget alone does not change dashboards. Application is an explicit separate action and result.

## Contract

`Goal.Start` accepts an optional host-only `dashboardTarget` containing `preset`, `expectedRevision` and ephemeral `clientId`. YoT first waits for configuration saves, confirms its local preset copy and captures its revision. Client configuration, adapter credentials and the origin identity are not passed to the model. Old callers without a target can still create widgets but cannot apply a dashboard.

The model returns one typed action:

```json
{"version":1,"action":"apply_dashboard","title":"Apply room dashboard","message":"Apply the saved room panel.","name":"panel","dashboardName":"Room panel","mode":"create"}
```

`name` identifies a container already saved and owned by the objective. `mode: "create"` refuses name collisions; `update` requires the named dashboard to exist. The host checks catalog membership using the static dashboard declaration. The endpoint `HomeAutomation.HomeGenie/Config/Client.PresetsApplyDashboard/<preset>` changes only this dashboard's layout under the same lock, revision precondition and atomic publication as normal preset saves. Standard widgets and unrelated settings remain intact; reapplying the same container retains its primary/named bindings. A new dashboard inherits the first existing dashboard's theme. No separate generic preset JSON is generated by the model.

The chat task stores a dashboard artifact (`kind`, `id` human dashboard name, `preset`, `widgetId`, committed `revision`, originating `clientId` and task `requestId`) independently of saved widget/program artifacts. Revisions retain the dashboard name, preset and container path. An application failure/conflict stops the runner and keeps previously confirmed widget results; it is not a request to regenerate them. A lost/uncertain commit receipt is not automatically retried. Inspect the preset before retrying it.

## Client behavior

Only the originating page may reload and open the applied dashboard automatically. The same preset/server must still be selected, the local fingerprint must be unchanged (checked again immediately before replacement), and the loaded revision must equal the result's committed revision. Other pages, newer server edits, switched presets, dirty local copies and history replay never trigger this automatic replacement. The existing Preferences badge/Update/Save As flow remains available. Open dashboard from a historical result requires the original up-to-date preset.

Version 1.0.6 handles native objects/dictionaries and JSON strings as well as HTTP bytes; this does not require regenerating the saved widgets or changing the preset.
